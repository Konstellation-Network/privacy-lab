## The `++nonce` trap

Worth recording because it cost a debugging cycle and would cost anyone else one.

`PrivacyPool.deposit` computes the deposit label with a *pre*-increment:

```solidity
uint256 _label = uint256(keccak256(abi.encodePacked(SCOPE, ++nonce))) % SNARK_SCALAR_FIELD;
```

So the first deposit's label uses nonce **1**, not the `0` returned by
`pool.nonce()` beforehand. Using 0 builds a commitment the pool never inserted.
The proof still generates and still verifies — it is a valid proof about a
different tree — and the only symptom is `UnknownStateRoot()` at submission.

A wallet implementation that gets this wrong produces unspendable deposits with
no error at deposit time. Anything we build on this should derive the label from
the `Deposited` event rather than recomputing it.

## Honest scope

**Proven:** the protocol works on Konstellation — EVM semantics, EC precompiles,
Poseidon, the Lean IMT, UUPS proxies, Groth16 verification, native-asset handling.

**Not proven:**

- **Relayer.** Threat model §4 calls the gas-linkage gate non-negotiable, and this
  test uses `vm.prank` on a relayer address rather than a running relayer service.
  A withdrawal where the recipient funds their own gas relinks them publicly, so
  this remains the most important open item.
- **D14 perimeter.** [004](004-d14-perimeter-analysis.md) and
  [008](008-asp-changes-the-d14-picture.md) are still analysis. The
  `x-compliance` binary is built but has not been run against a pool.
- **Wallet scanning** (threat model P4).
- **Anything about proof generation time on consumer hardware** — the prover ran
  under `--ffi` on a dev machine and the test did not measure it.

This is a feasibility result on a local single-node chain. It is not a security
review of Privacy Pools, and it says nothing about whether a pool *should* ship —
that is threat-model Q1/Q2, and remains a supervisor decision.
